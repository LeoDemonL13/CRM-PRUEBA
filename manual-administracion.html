Crear usuarios y asignar perfiles

1

Crear cuenta

Supabase → Authentication → Users → Add user. Define correo y contraseña y confirma el correo.

2

Ejecutar instalador

Si es una base nueva, ejecuta SQL_MAESTRO_CRM.sql una sola vez.

3

Asignar rol

Ejecuta crm_asignar_rol_por_correo con administrador, jefe_almacen, almacen, compras, proyectos o consulta.

4

Completar perfil

El usuario inicia sesión y captura su nombre, puesto, departamento y foto.

5

Probar permisos

Abre una ventana privada, inicia con esa cuenta y confirma que solo aparezcan los apartados autorizados.

select public.crm_asignar_rol_por_correo('correo@skilled.mx','jefe_almacen',true);
La cuenta admin.almacen@skilled.mx debe usar el rol jefe_almacen, no administrador. El archivo SQL_MAESTRO_CRM.sql lo configura.

Capacidad y almacenamiento en Supabase

Separa dos consumos: base de datos (filas, movimientos, proyectos) y Storage (PDF, imágenes, comprobantes y GIF).

PlanReferencia actualInterpretación para este CRM
Free1 GB de archivos; límite global de archivo de 50 MB; la base entra en modo de solo lectura al superar 500 MB de datos.Adecuado para pruebas, no para operación crítica prolongada.
Pro100 GB de archivos incluidos, 8 GB de disco por proyecto y cobro por excedente.Opción recomendada para producción inicial con PDF e imágenes.
Las cuotas y precios pueden cambiar. Revisa la página de precios de Supabase antes de contratar.
Cómo reducir consumo
Comprime imágenes, guarda una sola copia de cada PDF, elimina archivos huérfanos con un proceso controlado y evita subir videos al mismo bucket.
Buckets sugeridos
documentos-compra (privado), comprobantes (privado), herramientas (privado), vehiculos (privado) y avatares (privado o público controlado).
Seguridad
Supabase Storage usa RLS. Un bucket privado requiere políticas de lectura, carga, actualización y borrado; nunca expongas service_role en el navegador.

Publicar el CRM en Internet

1

Repositorio privado

Crea un repositorio en GitHub y sube el contenido de la carpeta CRM_SKILLED_COMPLETO. No subas service_role, secretos ni contraseñas.

2

Crear Pages

Cloudflare → Workers & Pages → Create application → Pages → Import an existing Git repository.

3

Configurar

Rama de producción main. No hay comando de compilación. Directorio de salida: raíz del repositorio.

4

Primera publicación

Prueba el subdominio pages.dev. Comprueba inicio de sesión, buscador, cámara y PDF.

5

Dominio

Pages → Custom domains → agrega crm.skilledmx.cloud. Si el DNS está en otro proveedor, crea el CNAME solicitado después de asociarlo en Pages.

6

Supabase Auth

Authentication → URL Configuration. Site URL: dominio final. Añade redirect del dominio final y localhost para desarrollo.

7

Ramas

Usa desarrollo para pruebas y main para producción. Cada push a main publica automáticamente.

8

Prueba final

Inicia sesión con cada perfil, realiza una entrada pequeña y genera un ticket.

Una carpeta para todos los perfiles

Todos los usuarios abren la misma URL y descargan los mismos archivos. La diferencia se decide después de iniciar sesión:

  1. 1. Supabase Auth valida correo y contraseña.
  2. 2. perfiles_usuario devuelve rol y estado activo.
  3. 3. auth-guard.js?v=75"guide-danger rounded-r-xl p-4 mt-5 text-[11px] leading-6 text-rose-200">Ocultar un botón no es seguridad suficiente. La protección real debe existir también en Supabase mediante RLS y funciones con validación de rol.

Usar una laptop vieja como servidor

Es técnicamente posible instalar Supabase autohospedado con Docker Compose, pero no es la opción recomendada para iniciar producción mañana.

AspectoSupabase administradoLaptop autohospedada
DisponibilidadOperada por el proveedor.Depende de electricidad, Internet, disco y mantenimiento local.
SeguridadPlataforma administrada más configuración propia.Tú actualizas SO, Docker, firewall, certificados y secretos.
BackupsBackups administrados en planes pagados; exportación manual en Free.Debes automatizar copias locales y externas y probar restauración.
EscalabilidadSe amplía por plan.Limitada por CPU, RAM, SSD y enlace de Internet.
Uso recomendado de la laptop
Servidor de pruebas, réplica de respaldo, laboratorio o almacenamiento secundario, no único servidor productivo.
Si decides autohospedar
Instala Linux estable, Docker y Docker Compose; usa SSD, respaldo externo, UPS, cable Ethernet, monitoreo, actualizaciones y un dominio HTTPS. Supabase recomienda Docker para self-hosting.
Exponer sin IP pública
Cloudflare Tunnel puede publicar un servicio mediante conexiones salientes, sin abrir puertos entrantes. Aun así, debes proteger el origen y mantener el servidor.
Migración futura
La base puede restaurarse de Supabase administrado a una instancia autohospedada, pero los objetos de Storage requieren un proceso separado.

Backups y recuperación

1

Código

GitHub privado conserva versiones. Etiqueta cada liberación estable.

2

Base de datos

En Free ejecuta exportaciones periódicas con Supabase CLI db dump o pg_dump. En planes pagados revisa Database → Backups.

3

Storage

Los backups de base no restauran los archivos borrados de Storage. Copia buckets de forma independiente.

4

Prueba

Una copia que nunca se restauró no está verificada. Haz una prueba mensual en un proyecto separado.

5

Plan de desastre

Documenta quién restaura, dónde están las claves, cuánto dato se puede perder y cuánto tiempo puede estar fuera de servicio.

⚿

Seguridad antes de producción

Obligatorio

  • • RLS habilitado en tablas y Storage.
  • • Solo publishable key en el navegador.
  • • service_role únicamente en servidor seguro.
  • • 2FA en GitHub, Supabase y Cloudflare.
  • • Usuarios individuales, no cuentas compartidas.
  • • HTTPS y dominio final configurado.

Revisión

  • • Desactivar empleados que ya no requieren acceso.
  • • Revisar políticas de lectura y escritura.
  • • Rotar secretos expuestos.
  • • No subir .env ni exportaciones con datos a GitHub.
  • • Limitar archivos por tipo y tamaño.

Flujo de cambios sin detener producción

1

Crear rama

Trabaja en desarrollo o una rama por cambio.

2

Vista previa

Cloudflare crea despliegues de vista previa. Prueba con una cuenta de prueba y una base de prueba cuando el cambio toque inventario.

3

Revisión

Ejecuta auditar.py, revisa consola del navegador y completa la lista de pruebas.

4

Publicar

Fusiona a main solo cuando la prueba sea correcta.

5

Rollback

Si falla el frontend, vuelve al despliegue anterior. Si falla SQL, restaura desde backup o aplica una migración correctiva; no edites datos a ciegas.
